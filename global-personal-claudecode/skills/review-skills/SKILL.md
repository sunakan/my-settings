## 制約

**git 操作は一切行わないこと**（commit・add・push・status・diff 等すべて禁止）。

## 調査対象の特定

引数: `$ARGUMENTS`

以下の順で SKILL.md の場所を特定する:

1. `$ARGUMENTS` が空 → 現在のディレクトリに `SKILL.md` があるか確認
2. `$ARGUMENTS` が `/` を含むパス → そのパスを直接 Read
3. `$ARGUMENTS` が名前のみ → 以下の順に探す:
   - `.claude/skills/$ARGUMENTS/SKILL.md`（プロジェクトスコープ）
   - `~/.claude/skills/$ARGUMENTS/SKILL.md`（個人スコープ）

場所が特定できたら、**SKILL.md を Read ツールで読み込む**。
同じディレクトリにある supporting files（`*.md`, `*.sh`, `*.py` など）も `ls` で確認する。

## レビュー手順

SKILL.md の内容を読んだあと、以下の項目を**全て**チェックする。

### チェック [1] Frontmatter の過不足

| フィールド | チェック内容 |
|-----------|------------|
| `description` | 存在するか。Claude が「いつ呼ぶか」を判断できる具体性か（「〜するとき」「〜が必要なとき」の形が理想）。最初の一文だけで呼び出し判断できるか |
| `description` + `when_to_use` 合計文字数 | 1,536 文字以内か（超過すると context 内で切り詰められる） |
| `argument-hint` | 引数を受け取るスキルに記載されているか |
| `arguments` | 複数引数を使うなら名前付き定義があるか（`$0/$1` より `$name` の方が保守性が高い） |
| `disable-model-invocation` | 副作用の大きい操作（デプロイ・コミット・削除・本番操作）に `true` が付いているか |
| `allowed-tools` | 繰り返し確認が出るツールが事前承認されているか |
| `context` | スキルが独立して完結する処理（調査・生成・更新など）なら `context: fork` を付けているか。付けないと中間処理がメインコンテキストを汚染する。書き込みを含む場合も `context: fork` のみで問題なし |
| `agent` | `context: fork` を付ける場合のみ確認。読み取り専用なら `agent: Explore`、書き込みを含むなら省略（`general-purpose` がデフォルト）。`context: fork` なしで `agent` だけ書いても無視される |

### チェック [2] 本文（Body）の品質

| 項目 | チェック内容 |
|-----|------------|
| 行数 | `wc -l` で確認。500 行を超えていたら supporting files への移動を提案する |
| 文体 | 命令形（「〜せよ」「〜する」）になっているか。説明文（「このスキルは〜する」）は不要 |
| 動的コンテキスト | `git status` やファイル一覧など、実行時に変わる情報を `` !`command` `` で取得しているか |
| 引数展開 | `$ARGUMENTS`・`$0`・名前付き引数の宣言と使い方が一致しているか |
| 具体性 | ファイルパスやコマンドが具体的か（「ファイルを見ろ」ではなく「`webapp/go/*.go` を見ろ」） |
| Supporting files | 仕様書・長いサンプル・テンプレートを本文に直書きしていないか。あれば外部ファイルへの移動を提案する |
| フォールバック | 引数なしや想定外入力への対処が書かれているか |

### チェック [3] サブエージェントパターン（Agent tool を使う場合のみ）

以下を確認する:

- **並列起動の明示**: 複数 Agent を使うなら「全 Agent を1メッセージ内に並べる」という指示があるか
- **プロンプトテンプレート**: 各 subagent へ渡すプロンプトが具体的に記載されているか
- **待機・集約の順序**: B-N 完了後に集約 Agent を起動するという順序が明示されているか
- **subagent type**: 読み取りのみなら `Explore`、書き込みがあれば `general-purpose` を指定しているか
- **context: fork の有無**: 独立した調査タスクに `context: fork` を使っているか（使いすぎにも注意）

### チェック [4] セキュリティ・安全性

| 項目 | チェック内容 |
|-----|------------|
| 破壊的操作 | `rm -rf`・`force push`・本番デプロイなどに `disable-model-invocation: true` があるか |
| 秘密情報 | トークン・パスワード・API キーがハードコードされていないか |
| `allowed-tools` の過剰許可 | `Bash` 全体を許可するなど広すぎるパターンがないか（`Bash(git *)` のように絞るべき） |
| `` !`command` `` の安全性 | shell injection につながりうるユーザー入力が直接展開されていないか |

## 出力先への書き込み

レビュー結果は `.claude/SKILLS_REVIEW.md`（プロジェクトルートの `.claude/` ディレクトリ）に書き出す。

**ファイルの扱い**:
- ファイルが存在しない → 新規作成
- ファイルが存在し、同じスキル名のセクション（`## <skill-name>`）がある → そのセクションを Edit で上書き
- ファイルが存在するが同名セクションがない → ファイル末尾に追記

**書き込むフォーマット**:

```markdown
## <skill-name>

> レビュー日時: <YYYY-MM-DD>
> ファイル: <SKILL.md の実際のパス>

### 総評
<2〜3文。スキルの目的と全体的な品質の評価>

### ✅ 良い点
- <具体的に何が良いか（ファイル内の該当箇所を示す）>

### ⚠️ 改善提案（任意対応）
- **<項目>**: <現状の問題> → <改善案（コード例あり）>

### ❌ 問題点（要修正）
- **<項目>**: <問題の内容と、修正後のコード例>

### 修正後の frontmatter サンプル（変更がある場合のみ）
\`\`\`yaml
---
<修正後の frontmatter を記載>
---
\`\`\`

---
```

ファイルが存在する場合は最初に Read してから、適切な方法（新規 Write または Edit）で更新する。

## レビュー後のアクション

`.claude/SKILLS_REVIEW.md` への書き込みが完了したら、会話上にも同じ内容を出力する。

その後、以下を確認する:

- ❌ 問題点がある場合: 「SKILL.md を修正しますか？」と聞き、承認されたら SKILL.md を Edit で更新する
- ⚠️ 改善提案のみの場合: 「適用しますか？」と聞き、ユーザーが選択した項目のみ更新する
- ✅ のみの場合: 修正不要とだけ伝える
